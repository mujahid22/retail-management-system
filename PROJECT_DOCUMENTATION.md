## 1. Project Overview

ToyWorld Retail Management System is a full-stack retail application built entirely in Python using Streamlit as the web framework and Supabase (PostgreSQL) as the cloud-hosted persistent database. The project was conceived as a real-world demonstration of an end-to-end retail management platform — from cashier-facing point-of-sale transactions to executive-level analytics dashboards and IT administration tools.

The application is role-gated: three distinct user roles (Cashier, Store Manager, IT Manager) each see a different subset of pages tailored to their responsibilities. All data entered via the POS terminal persists to Supabase and immediately reflects in the analytics dashboard — with no file system dependency, making it fully cloud-deployable.

### Key Features

- **Point of Sale terminal** — product scanner, cart builder, state-based tax calculation, receipt modal
- **Star schema data model** — fact_sales joined to 4 dimension tables, viewable in a table explorer
- **Sales Analytics Dashboard** — 6 KPI cards and 16 interactive Plotly charts across 4 tabs
- **Admin Hub** — session tracking, structured system event log, and Supabase health panel
- **Role-based access** — Cashier (POS only), Store Manager (POS + Analytics), IT Manager (all pages)
- **Persistent cloud storage** — all transactions, sessions, and logs survive restarts and redeployments
- **Synthetic data engine** — idempotent seeder generating 10,000 realistic sales rows with seasonality

### Application Pages

| Page | File | Roles | Purpose |
|---|---|---|---|
| Login | `app.py` | All | Role selector, session init, sidebar navigation |
| Point of Sale | `1_Transaction.py` | All | Live POS terminal with receipt modal |

| Sales Analytics | `3_Analytics.py` | Store Mgr + IT Mgr | 16 Plotly charts + 6 KPI cards |
| Admin Hub | `4_Admin_Hub.py` | IT Manager | Sessions, event logs, health panel |

## 2. Datasets Used

The application uses entirely synthetic data generated programmatically using the Python Faker library (seed: 42) combined with hardcoded domain reference data. No external third-party datasets were sourced. All data is modelled as a star schema in Supabase and generated on demand via the `seed_database()` function.

### Star Schema Tables

| Table | Rows | Key Columns | Source |
|---|---|---|---|
| `fact_sales` | ~10,000 | sale_id, transaction_id, qty, unit_price, discount, tax, total_amount, payment_mode | Generated by `build_fact_sales()` |
| `dim_customer` | 500+ | customer_id (hash), customer_name, email, phone, age_group, gender | Faker (en_US), seed=42 |
| `dim_product` | 300+ | product_id, product_name, category, sub_category, brand, sku, unit_cost, unit_price | Hardcoded categories + Faker brands |
| `dim_date` | 730 | date_id (YYYYMMDD), full_date, year, quarter, month, week_of_year, day_of_week, is_weekend | Date range: today minus 2 years |
| `dim_geography` | 50 | geography_id, city, state, region, zip_code | Hardcoded 50 US city-state map |
| `session_log` | Live | session_id, role, login_time, logout_time, duration_mins | Logged on every login/logout |
| `system_log` | Live | log_id, timestamp, level, source, event, message | Logged on every app action |

### Data Characteristics

| Dimension | Detail |
|---|---|
| Date range | Rolling 2-year window ending on today's date — recalculated each time the seeder runs |
| Product categories | 15 categories (Action Figures, Board Games, Dolls, Educational, etc.) with 4 sub-categories each |
| Brands | 15 fictional toy brands: ToyWorld, PlayMaster, KidZone, FunFactory, BrightPlay, etc. |
| Geography | 50 real US cities mapped to states and one of 4 US Census regions |
| Seasonality | Holiday (Nov–Dec) ×3.5 sales weight · Spring (Mar–Apr) ×1.5 · Summer (Jun–Aug) ×1.2 |

| Payment modes | Cash, Credit Card, Debit Card, Digital Wallet, Store Credit |
| Discount rates | 0%, 5%, 10%, 15%, 20%, 25% — weighted toward 0% (50% of transactions) |
| Cart sizes | 1–5 items per transaction — weighted toward single-item purchases (40%) |
| Price range | Unit cost $3–$85, margin 35–65%, resulting in unit prices roughly $5–$140 |

## 4. Iterations & Debugging Cycles

The most technically complex part of the session was the Supabase data seeding process. What appeared to be a straightforward database operation revealed several layers of nuanced behaviour in the Supabase REST API and supabase-py client library.

---

### Iteration 1 — Hardcoded 2024–2025 Date Range

**Problem:**
First seeding attempt used `date(2024, 1, 1)` to `date(2025, 12, 31)` hardcoded in `seed_database()`. User noticed the analytics showed old data, not current dates.

**Resolution:**
Changed to rolling dates: `end = date.today()`, `start = date(today.year-2, today.month, today.day)`.

---

### Iteration 2 — Single DELETE Call (PostgREST Row Limit)

**Problem:**
Attempted to clear tables before reseeding using a single `.delete().neq('sale_id', '').execute()` call per table. With 10,000 rows in `fact_sales`, PostgREST's default `max_rows` cap of 1,000 meant only 1,000 rows were deleted. The remaining 9,000 rows held FK references, preventing dimension table deletion. Result: duplicate key error on re-INSERT.

**Resolution:**
Switched to a loop approach — call DELETE repeatedly until confirmed empty.

---

### Iteration 3 — Loop Using `result.data` (Silent Empty Return)

**Problem:**
Changed to a `while` loop checking `if not result.data: break`. However, supabase-py v2 uses `Prefer: return=minimal` by default after a DELETE, meaning `result.data` is always `[]` regardless of how many rows were actually deleted. The loop exited after one batch.

**Resolution:**
Changed to use a COUNT query: `.select(id_col, count='exact').execute().count`

---

### Iteration 4 — COUNT Query Returning None

**Problem:**
The `.count` attribute on the supabase-py `APIResponse` object returns `None` unless the server sends the `Content-Range` header. The expression `(result.count or 0)` evaluated to `0` every time, so the loop still exited after one DELETE batch.

**Resolution:**
Changed emptiness check to `.select(id_col).limit(1).execute().data` — a plain Python list that is reliably empty (`[]`) when no rows exist.

---

### Iteration 5 — Supabase RPC Truncation Attempt

**Problem:**
Created a PostgreSQL stored function `truncate_star_schema()` with `TRUNCATE ... CASCADE` and called it via `client.rpc()`. However, the anon role lacked `EXECUTE` permission on the function, causing a silent failure — RPC returned 200 OK but no rows were deleted.

**Resolution:**
Added `GRANT EXECUTE ON FUNCTION truncate_star_schema() TO anon` in Supabase SQL Editor.

---

### Iteration 6 — UUID-Based `customer_id` Across Reseeds

**Problem:**
Even with RPC working, a new error appeared: duplicate key on `dim_customer_email_key`. Root cause: `customer_id` was generated as `str(uuid.uuid4())[:12]` — system randomness, completely ignoring the Faker seed. Each reseed generated **different** customer IDs for the **same** emails. Upsert on PK tried to INSERT a new row, hitting the email unique constraint.

**Resolution:**
Changed `customer_id` to a deterministic MD5 hash of the email address: `"C" + hashlib.md5(email.encode()).hexdigest()[:11].upper()`. Same email always produces the same ID.

---

### Iteration 7 — Stale Python Bytecode Cache

**Problem:**
Despite multiple code fixes, the Streamlit app kept running old code. The traceback showed function names (e.g. `_insert_batches`) that had been renamed, and line numbers pointing to deleted code. Root cause: Streamlit caches imported modules in `sys.modules` across reruns within the same process. Even stopping and restarting Streamlit did not always clear the `.pyc` bytecode cache.

**Resolution:**
Deleted all `__pycache__` directories and `.pyc` files, then ran `seed_database()` directly via command line (fresh Python process, guaranteed clean import). Added `importlib.reload()` in the Data Model page button handler as a permanent fix.

---

### Iteration 8 — Windows CP1252 Unicode Error

**Problem:**
Print statements in `data_generator.py` used Unicode characters (`→` U+2192, `…` U+2026) that caused `UnicodeEncodeError` on the Windows CP1252 console terminal.

**Resolution:**
Replaced all non-ASCII characters in print statements with ASCII equivalents: `->` and `...`

---

### Iteration 9 — Final Hybrid Truncation Strategy

**Problem:**
No single approach reliably cleared all 10,000 rows with FK constraints intact.

**Resolution:**
Settled on a robust three-layer approach: (1) Try RPC `TRUNCATE CASCADE` for speed, (2) verify each table using `.limit(1).data`, (3) drain any non-empty tables using the DELETE loop with `.limit(1)` emptiness check. Combined with deterministic hash IDs and upsert semantics, the seeding became fully idempotent. Confirmed: *"Done. Seeded 10,000 rows from 2024-06-02 to 2026-06-02."*

## 5. Learnings & Observations

### Supabase / PostgREST Specifics

- **DELETE row limit:** PostgREST caps DELETE at `max_rows` (default 1,000) — the same limit that applies to SELECT queries. Bulk deletion of large tables requires a looped approach.
- **Silent empty result after DELETE:** supabase-py v2 returns `result.data = []` after every DELETE by default (`Prefer: return=minimal`). Use a follow-up `SELECT .limit(1)` to confirm emptiness.
- **`.count` returns None:** The `.count` attribute returns `None` unless the server sends the `Content-Range` header. The pattern `(result.count or 0)` evaluates to `0` even when rows remain.
- **RPC permissions:** `TRUNCATE` via a stored function requires an explicit `GRANT EXECUTE` to the anon role — even with `SECURITY DEFINER`. Failed calls may return 200 OK with no visible effect.
- **Row Level Security:** RLS is enabled by default on tables created via the Supabase UI. Disable it or add permissive policies for the anon key to read/write.
- **FK constraint ordering:** Foreign key constraints are enforced at the database level. Always delete the fact table (`fact_sales`) before dimension tables.
- **Upsert on non-PK unique column:** `on_conflict="email"` attempts to UPDATE existing rows including the PK — safe only when no FK references point at the old PK value.

### Streamlit Specifics

- **Module caching:** Streamlit caches imported modules in `sys.modules` across reruns. Editing a source file does not reload an already-imported module. Use `importlib.reload()` or run code in a fresh subprocess.
- **Bytecode caching:** Python `.pyc` files persist across Streamlit restarts and can cause the app to run stale code. Delete `__pycache__` directories to force recompilation.
- **Cache invalidation:** After seeding new data, `st.cache_data.clear()` must be called explicitly to force a fresh database read.
- **`@st.cache_resource`:** Correct decorator for a Supabase client singleton — persists for the lifetime of the server process and is shared across all user sessions.
- **Streamlit Cloud dependencies:** Installs from `requirements.txt` (pip), not from `pyproject.toml` or `uv.lock`. A separate `requirements.txt` is required even if the local project uses uv.
- **`runtime.txt`:** Required by Streamlit Cloud to specify the Python version. Without it, the platform defaults to an older version that may be incompatible.

### Python / Windows Specifics

- **CP1252 encoding:** Windows uses CP1252 by default. Unicode characters like `→` (U+2192), `…` (U+2026), and `✓` (U+2713) cause `UnicodeEncodeError` in `print()` statements. Set `PYTHONIOENCODING=utf-8` or use ASCII-only output.
- **Deterministic IDs for idempotent seeding:** UUIDs generated with `uuid.uuid4()` use system randomness and are never reproducible. Hash-based IDs derived from a stable field (e.g. MD5 of email) produce the same ID every time, making upsert on PK a safe reseed strategy.
- **Faker seed scope:** `Faker.seed(42)` must be called inside `seed_database()` — not just at module level — to guarantee the same data sequence across multiple calls in the same Python process.

### Vibe Coding Workflow Observations

- **Planning before coding pays disproportionately.** The `EnterPlanMode` step produced a 10-phase migration plan that correctly anticipated FK constraint ordering, pagination limits, and module caching issues — even if execution still required debugging iterations.
- **Infrastructure debugging takes longer than application logic.** The seeding bug consumed 9 iterations; the entire UI redesign was completed in one pass after an approved design proposal.
- **Show before implement.** Presenting a written design proposal for the UI redesign before writing any code prevented wasted work. The user redirected the design in text, not in code.
- **Run code outside the app.** Running `seed_database()` directly via `python -c` bypassed Streamlit's module cache and gave clean terminal output that immediately exposed the root cause.
- **Role-based access defined early guides everything.** Getting the role structure right upfront shaped every feature decision — which pages to build, which metrics to expose, and how to structure navigation.
- **The gap between "code on disk" and "code running" is a real trap.** Bytecode and module caching in Streamlit create a disconnect that looks like a fix is not working when it actually is. Always verify with a fresh process.
- **Confirm before destructive operations.** Presenting the staged file list before committing confirmed no secrets were being pushed to the public repository.
